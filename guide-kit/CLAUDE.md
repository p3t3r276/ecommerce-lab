# Guide kit: hands-on guides for the e-commerce microservices lab

This repo produces **weekly Markdown guides** that the user follows to build the lab (`shoplab`) by hand. Agents never write into the user's repo. They design each step, build a **reference implementation** that really builds and passes tests, and write guides whose snippets are copied from that reference.

## Language
- Talk to the user in Vietnamese (address them as "bạn").
- `guides/**` and `reviews/**` are for the user to learn from: write them in Vietnamese. Keep code, identifiers, commands and established technical terms in English.
- Everything else is in English: `decisions.md`, `design/**`, `build-log/**`, `plans/ISSUES.md`, `shared/**`, code comments.

## Layout
```
plans/source/          the two original plans (read-only, never edit)
plans/v3/, plans/detail/, plans/index.json, plans/sessions.tsv
                       slices generated by tools/split-plans.py (never edit)
plans/ISSUES.md        known problems in the plans, each assigned to a step
decisions.md           every decision; overrides the plans (append-only)
design/sN.md           design of step N: contracts, conventions, questions, session kinds
shared/sN.txt          files that must be identical in the user's repo (from design/sN.md)
reference/             reference implementation (its own git repo, = shoplab root)
build-log/wNN.md       what the builder did per session: commands, results, errors, experiments
guides/sN/wNN.md       the weekly guide for the user (Vietnamese)
reviews/wNN.md         review of the user's own code (Vietnamese)
notes/sN.md            written by the user: deviations they want to keep, questions
kit.env                SHOPLAB_PATH=<path to the user's repo>
```

## Read only what you need
Never read `plans/source/*` whole (about 200 KB). Use the slices:
- `plans/index.json` maps steps → weeks → sessions → files.
- `plans/v3/steps/sN.md` (roadmap bullets + gate), `plans/v3/domain/<context>.md`, `plans/v3/domain/events.md`, other `plans/v3/NN-*.md` sections.
- `plans/detail/sN/wNN.md` (one week: goal + 4 sessions), `plans/detail/sN/_step.md`, `plans/detail/testing/*.md`.

## Step lifecycle
1. `/design-step SN` → `design/sN.md` with `status: draft`.
2. `/decide SN` → the user answers the open questions; decisions appended to `decisions.md`; `shared/sN.txt` written; design `status: approved`.
3. `/build-reference` → one week at a time, in session order, inside `reference/`.
4. `/write-guides` → `guides/sN/wNN.md` for every built week without a guide.
5. The user codes in their repo, runs `bash tools/sync-to-shoplab.sh SN` to copy shared files, optionally `bash tools/export-guide.sh SN` to write `docs/guides/ShopLab-SN.md` there (the location v3 expects), then `/review-my-code wNN`.
6. The user writes `notes/sN.md`; the next `/design-step` reads it.

Agents stay **at most one step ahead**: `/design-step SN` requires the reference tag `s(N-1)-done` (except S0).

## Reference repo conventions
- `reference/` is the root of a `shoplab` repo, with its own git history. Paths in the plans (`src/...`, `tests/...`) are relative to it.
- **One commit per session**, message `bNNN: <short task>` (NNN = session number with 3 digits). A session without code changes still gets `git commit --allow-empty`.
- Tag `wNN` after the last session of each week; tag `sN-done` when the step gate passes.
- Branches follow the plan, with `master` as the default branch (D-010, D-012): each step is built on `step/sN-<name>`. In the gate session, only if the gate passes: `git checkout master && git merge --no-ff step/sN-<name>`, tag `sN-done` on the merge commit, then `git checkout -b step/s(N+1)-<name>`. If the gate fails: no merge, no tag. `master` therefore only holds steps that passed their gate.
- Never rewrite history that is already tagged. A fix after a tag is a new commit `bNNN-fix: ...` and is mentioned in the build log.

## Session kinds (assigned in design/sN.md)
- `scaffold`: boilerplate, config, CRUD, wiring. Guide shows the code directly.
- `core`: the patterns the lab exists to teach (outbox, inbox, publisher, consumer host, saga, StockLevel and concurrency, Lua scripts, pricing engine, projections, POS sync). Guide gives the task, hints and the contract signatures first; the solution sits in a collapsed `<details>` block.
- `test`: writing tests. Usually shown directly; tests of `core` code may be `core` too.
- `manual`: UI clicks or installs (Keycloak console, tools). Guide explains the steps; the builder produces the end artifact (for example the realm JSON).
- `gate`: running the step gate and writing notes.

## Honesty rules
- Never claim a command was run or a test passed unless it was. Every session in `build-log/wNN.md` states its verification level: `test`, `build`, `run`, `manual`, or `unverified` with a reason.
- Snippets in guides are copied from the reference commit, never rewritten from memory. Trimming with `// ...` is allowed.
- "Try changing" experiments in guides are marked either **đã chạy thử** (the builder ran it, result in the build log) or **dự đoán** (expected, not run).
- If something needed is not in `decisions.md`, `design/sN.md` or the plans, do not invent it: stop and report it (builder), or add it to the step's open questions (designer).

## Safety
- Never write outside this repo, except that `tools/sync-to-shoplab.sh` and `tools/export-guide.sh` write into `$SHOPLAB_PATH` when the user runs them. Agents never run these two scripts.
- Never put real secrets in files. Dev credentials from the plans (`Passw0rd!`, Keycloak `admin/admin`) are allowed only where the plans put them.
- Do not leave long-running processes behind (`aspire run`, containers started by hand). Use `timeout`, verify, stop.
